# 影響分析格式

> 任務技能產出影響分析、變更計畫或審查結論時使用本格式。內容寫入 `../TODO.md` 當前項目或 `../resources/evidence/<WORK-ITEM-ID>/`，本範本本身不填寫。

## 1. 分析基準
- 版本：base revision 與工作樹狀態（是否含未提交修改）。
- 平台與設定：本次涵蓋的平台、晶片、建置入口與設定來源；未涵蓋者列入第 5 節。
- 方法：靜態追查、文字搜尋、工具或建置；註明工具與版本。

## 2. 影響點
| # | 檔案:行 | 符號或位置 | 關係類型 | 平台 | 確定度 | 說明 |
|---|---|---|---|---|---|---|

- 關係類型：直接呼叫、table dispatch、共享資料或記憶體別名、條件編譯、協定或暫存器契約、ISR→main、初始化或序列順序、文件。
- 確定度：`已確認` 指靜態關係已由來源位置證實；`候選` 指文字參照或推論尚未證實。兩者都不代表硬體行為已驗證。
- 搜尋得到的是文字參照，不可直接稱為呼叫者；經函式表、指標或巨集間接到達者需註明路徑。

## 3. 變更範圍
採最小變更：只改達成需求所必需的位置，其餘依下列三類明列。

| 類別 | 項目 | 依據 | 理由 |
|---|---|---|---|
| 要改 | | 需求／根因 | |
| 保留但停用 | | | |
| 不改 | | | |

- 「要改」每一列的依據欄必填，只能是：`需求`（引用需求原文）或 `根因`（引用第 2 節影響點編號）。填不出依據的項目不得留在「要改」，移到第 6 節。
- 「建議同時」「順便」「一併」「預防」等附加修改，一律視為無依據。

- **保留但停用**：失去呼叫者的共用 helper、API、事件處理、診斷欄位與設定開關，預設保留並以既有方式標示（例如註解、`unused` 屬性、`reserved` 位址），而非刪除。
- 需求是移除某項功能時，移除其入口與該功能專用的程式碼及狀態；共用 API、其他功能也會用到的資料與固定位址仍保留。
- 不搬動或壓縮固定 RAM 位址、記憶體 layout、事件列舉值、步驟表以外的序列；外部工具可能依賴它們。
- 不新增需求未要求的介面、巨集、服務、設定排除或行為；認為需要時列入第 6 節或待使用者確認，不寫進「要改」。
- 不為了一致性或預防而更改既有型別、寬度、存取方式或資料結構；根因只在單一定義時，只改那一個定義。
- 不順便清理、重新命名或重排無關程式碼；若發現值得清理的項目，列入第 6 節另開 work item。
- 刪除函式呼叫後檢查新增的 unused warning、未使用變數與死碼，並以最小方式處理，不關閉 warning。
- 單一平台的修改，需比對其他平台是否有同名定義或相同需求；不一致時列為待確認，不自行套用或忽略。

## 4. 驗證計畫
| 層級 | 內容與通過條件 | 必須實板 |
|---|---|---|

- 每個受影響平台各自 build；條件編譯分支需涵蓋非預設設定組合時一併列出。
- 時序、電氣、協定與使用者可見行為一律列為實板項目。

## 5. 未解析與未涵蓋
- **未找到**：已搜尋但沒有結果，寫出搜尋範圍。
- **未解析**：存在但無法靜態判定目標，例如函式指標、執行期選擇、外部工具。
- **未涵蓋**：本次沒有分析的平台、設定、binary、外部專案或文件。
- 「沒找到」不等於「無影響」；三者皆須明列，不可省略為無。

## 6. 範圍外發現
- 分析時發現、但不屬於本需求的疑似問題，附來源位置與確定度，不併入本次修改。

## 7. 交付前自我檢查
交付前逐項回答，任一項為「否」時先修正第 3 節再交付：
- [ ] 「要改」每一列都有 `需求` 或 `根因` 依據。
- [ ] 「要改」沒有新增需求未要求的介面、巨集、服務、設定排除或行為。
- [ ] 「要改」沒有更動既有型別、寬度、存取方式或資料結構；若有，依據為根因而非一致性。
- [ ] 失去呼叫者的共用程式碼、固定位址與列舉值已列在「保留但停用」或「不改」。
- [ ] 其他平台已比對，差異列為待確認。
- [ ] 第 5 節三種狀態都已填寫。
