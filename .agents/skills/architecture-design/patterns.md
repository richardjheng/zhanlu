# MCU 韌體常見模式與契約

> 本檔用於辨識專案**既有**的模式，並在修改、審查、移植時維持其契約，不是修改或重構的依據。
> - 每項修改仍須依 `../../templates/impact-analysis.md` 第 3 節，以需求或根因為依據；模式名稱不能當依據。
> - 既有程式違反契約、但不屬於本次需求或根因時，只列入影響分析第 6 節，不併入本次修改。
> - 不因本檔引入專案沒有的模式；`architecture-design` 也不例外。
> - 條文句型：「若既有程式採用 X，修改時須維持 Y，不可 Z」。無法從程式碼判定的契約標為待確認。

## 使用方式
1. 先辨識：依「辨識特徵」確認專案實際採用哪些模式，記下位置與實作方式。
2. 再對照：只檢查與本次變更相關的契約項目。
3. 結果寫入影響分析：受影響的契約列在第 2 節（關係類型對應「ISR→main」「共享資料」「table dispatch」等），無法確認的列在第 5 節。

## 1. 跨 context 傳遞
**辨識特徵**：ISR 內只設旗標、寫入佇列或喚醒 thread；`head`／`tail` index 的環形緩衝；service flag 或事件 bitmap。

- **ISR 延後處理**：若 ISR 只負責收集與排程，修改時須維持 ISR 不阻塞、不呼叫可能睡眠或長時間等待的函式；不可把原本在 main／thread 的工作移進 ISR。
- **旗標與事件**：若以旗標傳遞，須確認清除時機與讀取順序；「讀後清除」需原子完成，不可在讀與清之間遺失 ISR 新設的旗標。多個事件共用一個 bitmap 時，寫入方式須與另一側的存取方式一致（原子 OR／AND 或 critical section）。
- **SPSC ring buffer**：若既有程式採單一生產者、單一消費者 buffer，須維持 `head` 只由生產者寫、`tail` 只由消費者寫；index 存取須具原子性，由平台保證或既有同步機制保護，若宣稱 lock-free 另確認其成立條件；資料寫入須早於 index 更新（需要時加 barrier）；滿與空的判定方式（保留一格或計數）不可混用。
- **共用變數**：`volatile` 只保證不被最佳化掉，不保證原子性或順序；多位元組變數的讀寫跨越 ISR 時須確認保護方式。

**常見錯誤**：在 ISR 內做專案未允許的阻塞等待或同步輸出；多生產者寫入 SPSC buffer；index 寬度超過平台單次存取且未加保護；清旗標前未保存值。

## 2. 狀態機與有界等待
**辨識特徵**：`state × event` 表或 switch；步驟表（step、delay、等待條件）；1ms／10ms 等時段 service；`timeout`／`retry` 計數；debounce 計數；watchdog 餵狗點。

- **表驅動狀態機**：若既有程式以表定義轉移，先找出所有實際的轉移入口（表內與表外，例如 reset、錯誤恢復）；修改時沿用該轉移所屬的既有入口，不另開新入口。新增狀態或事件時同步更新表長、entry／exit 動作與非法轉移處理。
- **步驟表與序列**：若 power sequence 或初始化以步驟表執行，須維持步驟順序、delay 與等待條件；不把步驟拆成表外的直接呼叫，不搬動步驟編號（外部 log 或工具可能依賴）。
- **時段排程**：若採 cooperative 時段 service，修改時確認新增的執行時間不會讓其他 service 錯過其實際期限（依 SPEC 或既有量測，不以 service 週期當作期限）；無法確認時列為待驗證。
- **有界等待**：需要在限定時間內完成的操作（硬體交握、bus 交易、sequence 步驟等待）須有 timeout 與失敗路徑，失敗後硬體停在安全狀態。正常等待事件的閒置任務不適用此條。
- **非同步交易**：若交易可被取消或逾時，須處理逾時後才到的回覆（丟棄或以交易序號比對），取消後不可再寫入已釋放的 buffer 或已切換的狀態。
- **Debounce**（時間穩定條件）：訊號連續穩定達指定時間或次數才成立；按下與放開、插入與拔除的時間可不對稱，修改時不可擅自統一。
- **Hysteresis**（雙門檻轉移條件）：進入與離開使用不同門檻；不可把兩個門檻合併為一個，也不可只改其中一個而不確認間距。
- **Watchdog**：餵狗須以受監控工作的進度證據為條件；不可在缺少進度證據時持續餵狗（例如在 timer ISR 或等待迴圈內無條件餵狗）。初始化、燒錄與長操作期間的處理方式須沿用專案既有做法。

**常見錯誤**：需要有界完成的硬體等待迴圈沒有 timeout；修改 delay 未依 SPEC；逾時後未重設狀態；遲到回覆覆寫新交易結果。

## 3. 共享資料與硬體存取
**辨識特徵**：register 讀改寫巨集；寫 1 清除（W1C）的狀態位元；shadow 變數；ACPI EC space、H2RAM、mailbox；固定大小的 buffer pool 或交易 slot。

- **讀改寫（RMW）**：若同一 register 由多個 context 修改，RMW 須在保護範圍內完成。
- **W1C**：不可把讀出的 W1C 位元原樣回寫，否則會誤清其他狀態位元。純 W1C register 只寫入要清除的位元；RW 與 W1C 混合的 register 須依 register SPEC 組合寫入值（保留 RW 欄位、W1C 欄位只放要清除的位元）。清除時機依既有順序，不擅自調換。
- **Shadow register**：若硬體不可讀回而以 shadow 保存，所有寫入都須經過 shadow，不可繞過直接寫 register。
- **Host 共用記憶體與雙端交握**：須先寫完資料，再設旗標、發 SCI 或通知對方；固定位址、欄位寬度與位元組順序與 BIOS／driver／外部工具共用，不可搬動或改寬度；多位元組欄位須確認對方讀取時不會看到半更新的值。
- **靜態配置與 memory pool**：區分「儲存區建立」（編譯期或初始化期）與「區塊借還」（可在執行期）。須確認容量、耗盡時的處理、每個區塊的擁有者，以及逾時或取消後 DMA、硬體或 callback 是否仍持有該區塊；仍被持有時不可歸還或重用。
- **Buffer 生命週期**：傳給 DMA、ISR 或非同步 callback 的 buffer，在對方使用期間生命週期不可結束，也不可被覆寫；區域 buffer 只有在離開作用域前已確認對方完成（含逾時與取消路徑）時才安全。

**常見錯誤**：以 `|=` 清 W1C 狀態；先發 SCI 再寫資料；逾時後立即重用 DMA buffer；為對齊而改固定欄位寬度。

## 4. 輸出仲裁與恢復
**辨識特徵**：同一組 PWM、風扇、限流、LED 或 GPIO 輸出被多個模組寫入；override、force、limit 旗標；保存的「使用者設定值」與「目前輸出值」並存。

- **優先序**：若多方寫入同一輸出，須列出所有寫入者與優先序（例如保護 > thermal > power state > host 命令 > 使用者設定）；修改其中一方不可繞過仲裁直接寫硬體。
- **Override 與恢復**：覆寫解除時須回寫基準值（使用者設定或上一層的要求），不可停在覆寫值；確認負責恢復的是哪一方。
- **單位一致**：設定值與硬體原始值（百分比與 duty register）單位不同時，恢復路徑須做相同換算。

**常見錯誤**：thermal 降載解除後亮度或風扇停在降載值；power state 切換時 pattern 狀態機覆寫保護設定。

## 5. 靜態分派與編譯期約束
**辨識特徵**：command／ops／hook 函式表；`__weak` 或 weak symbol；X-macro 產生列舉與表；`static_assert`／`BUILD_ASSERT`；hook 註冊巨集與優先序。

- **Command 與 ops 表**：若以表分派，新增或刪除項目時須維持索引與列舉一致；命令編號與 host 或外部工具共用時不可重新編號，移除命令保留其編號為 reserved。
- **Hook 與優先序**：若以註冊機制呼叫 handler，須確認所有 handler 與執行順序；新增 handler 不可改變既有 handler 的相對順序，除非需求要求。
- **Weak symbol**：若板級或產品以強符號覆寫 weak 預設，修改預設實作時須檢查所有覆寫版本；移除覆寫會靜默回到預設行為，須列入影響分析。
- **編譯期檢查**：既有的 `static_assert`（表長＝列舉數、結構大小、欄位 offset）不可為通過 build 而刪除或放寬；修改表或結構時同步確認檢查仍成立。
- **X-macro**：若列舉與表由同一份清單產生，只修改那份清單，不另外手寫一份。

**常見錯誤**：只改表不改列舉；刪除命令後重排編號；板級覆寫函式遺漏新參數。

## C++ 專案（條件適用）
僅在專案以 C++ 撰寫相關模組時適用；exception、RTTI、heap、STL 是否允許，以 `../../project.md` 的專案限制為準，本檔不預設。
- **RAII guard**：若以物件管理 critical section、lock 或硬體資源，須確認所有提前 return 路徑都會釋放；不可在 ISR 內使用可能阻塞的 guard。
- **靜態物件初始化順序**：非區域靜態物件的動態初始化通常在 `main` 前完成，但可能延後，跨編譯單元的順序未指定；函式內 static 物件在首次執行到宣告時才初始化。不可依賴未保證的順序，建構子內不可存取可能尚未初始化的硬體或其他全域物件。
- **資源生命週期**：交給 ISR、DMA 或 callback 的物件，生命週期須涵蓋對方使用期間；不可傳入暫時物件。
- **程式碼大小**：template 與 inline 的展開可能改變 ROM 用量；修改時比較 map 檔前後的 size。
